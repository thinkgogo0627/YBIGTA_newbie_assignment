## 3. CoT Prompting이 Direct Prompting보다 좋은 이유

### 3.1 관찰

Direct는 세 설정 모두에서 CoT에 크게 못 미쳤고, shot 수에 대해 단조 증가하지도
않았다(3-shot 52% → 5-shot 40%). Direct 프롬프트는 "근거 없이 `Answer:` 뒤에 최종
답만 출력하라"고 지시하므로, 모델은 문제를 읽자마자 답 토큰을 생성해야 한다.

### 3.2 해석

**(1) 중간 계산을 저장할 공간이 없다.** MATH 문항 대부분은 두 단계 이상의 산술을
요구한다. Transformer는 한 토큰을 생성할 때 고정된 깊이의 연산만 수행하므로,
다단계 계산을 단일 토큰 위치에서 끝낼 수 없다. CoT는 생성된 토큰 자체를 작업
메모리로 사용해 이 제약을 우회한다.

**(2) Direct의 few-shot은 형식만 가르친다.** Direct 예시는 (문제, 답) 쌍이므로
예시에서 얻는 정보는 "짧게 답하라"는 출력 형식뿐이다. 반면 CoT 예시는 (문제, 풀이,
답)이라 **풀이 절차 자체**가 시연된다. 이것이 0-shot에서도 CoT가 70%를 내는 이유이고
(지시문만으로 절차를 유도), Direct가 shot을 늘려도 개선되지 않는 이유이기도 하다.

**(3) 답 형식 산출 실패가 줄어든다.** Direct에서 관찰된 다수의 `None` 중 일부는
모델이 짧은 답을 강요받은 상태에서 형식을 벗어난 출력을 낸 경우였다. CoT는 풀이를
전개한 뒤 마지막에 답을 배치하므로 파서가 답을 찾을 확률이 높다.

## 4. My Prompting 설계

### 4.1 출발점

지난 학기 수행한 multi-hop QA 멀티에이전트 과제에서 사용한 설계를 단일 호출
프롬프트로 이식하는 것을 목표로 했다. 원 시스템의 구성 요소 중 이식 가능한 것은
다음 세 가지였다.

| 원 설계 | 이식 형태 |
|---|---|
| Plan-and-Solve 기반 Decomposer | 답에 착수하기 전 2–4단계 계획을 먼저 확정 |
| Reflector의 ISREL/ISSUP 판정 | 좁게 열거된 검증 항목 |
| Self-RAG의 ISSUP 규율 (근거 인용 강제) | 각 계산 단계의 출처 명시 |
| 답 형식 규칙 (train dev 관찰 기반) | `\boxed{}` 형식 계약 + 정확값 강제 |

멀티에이전트 루프 자체는 이식하지 않았다. 원 시스템의 Reflector가 작동한 이유는
외부 근거(위키피디아 문서)와 대조하는 판정이었기 때문인데, MATH에는 대조할 외부
근거가 없어 순수 자기교정이 되기 때문이다. 또한 TPM 6,000 제약상 문항당 다중 호출은
현실적으로 불가능했다.

### 4.2 실패 사례 기반 규칙 설계

원 과제에서 사용한 방법론 — **dev 실패 사례를 관찰한 뒤 그 실패를 겨냥한 규칙을
프롬프트에 명시적으로 열거하는 것** — 을 그대로 적용했다. 초기 실행의 오답을 분류한
결과 다음 패턴이 반복적으로 관찰되었다.

**(a) 퇴화 반복(degenerate repetition)으로 인한 출력 절단**

Q37 `(26² − 24² − 10)² − 10²`에서 모델은 정답 8000을 정확히 산출한 직후
`However, we need to check if the expression can be simplified further.`로
이탈해 잘못된 전개(8100)를 20회 이상 반복하다 잘렸다. 최종 답이 산출되지 않아 오답
처리되었다. Q14도 동일한 구조의 실패였다.

→ **종결 규칙**: 결과를 얻으면 즉시 중단, 같은 값의 대안 형태 탐색 금지,
이미 계산한 양의 재유도 금지, 결과 도출 후 `However`로 문장 시작 금지.

**(b) 극값 문제에서 첫 후보 커밋**

Q4(세 연속 정수의 합인 최소 세제곱수)에서 729를, Q6(0과 2만으로 쓰는 30의 최소
배수)에서 2020200을 산출했다. 두 답 모두 **조건은 만족하지만 최소가 아니다.** 모델이
후보를 하나 찍고 조건 검증에 성공하면 최소성을 확인하지 않고 종료한다.

이는 원 과제의 오류 분석에서 관찰한 것과 동일한 구조다. 당시 Decomposer가
"paternal grandfather"를 mother-first 체인으로 분해한 뒤, CoT가 이미 잘못된 첫 hop을
교정하는 대신 **사후 정당화**로 작동했다. 잘못된 첫 커밋은 이후 추론으로 회복되지
않는다.

→ **극값 프로토콜**: smallest / least / greatest / largest가 포함된 문항은 후보를
먼저 제시하지 말고, 제약을 먼저 도출한 뒤 후보를 순서대로 나열해 조건을 만족하는
첫 번째를 취한다.

**(c) 묻는 대상 혼동**

Q19(`x⁶ − 3`을 `x + 1`로 나눈 몫)에서 마지막 항을 `−1` 대신 `−2`로 답했다. `−2`는
**나머지**다. 조립제법의 마지막 칸을 몫에 붙인 것으로, 산술 오류가 아니라 대상 혼동이다.

→ **대상 재확인**: 최종 답 직전에 무엇을 물었는지 한 절로 재진술
(몫인지 나머지인지, 개수인지 값인지).

**(d) 근사값 및 형식 이탈**

Q29 `3^{2x} + 19 = 10^x`에서 `1.259`를 산출했다(정답 2). 수치해로 접근한 것이다.

→ **정확값 강제**: 소수 근사 금지, LaTeX 표기 강제, 기약분수·유리화.

### 4.3 파서 계약

`extract_final_answer`의 동작을 확인한 결과, `\boxed{}` 추출이 `Answer:` 정규식보다
**항상 우선**한다. 즉 응답 어딘가에 `\boxed`가 하나라도 있으면 마지막 것이 최종 답으로
채점되고 `Answer:` 줄은 무시된다.

```
'check: \boxed{3} works\nAnswer: 7'  ->  '3'      # Answer 줄 무시
'**Answer:** 12'                     ->  '** 12'   # 마크다운 볼드로 파싱 파손
'### Answer\n12'                     ->  None
```

따라서 최종 답을 `Answer: \boxed{...}` 형태로 마지막 줄에 고정하고 그 뒤에 아무것도
쓰지 않도록 계약을 명시했다. 이는 마크다운 서식으로 인한 파싱 파손도 함께 막는다.

### 4.4 컨텍스트 배치

초기 실험에서 5-shot이 3-shot보다 낮게 나오는 현상을 관찰했다. 규칙 블록이 프롬프트
선두에 있는데 5-shot에서는 예시 약 2,000토큰이 규칙과 질문 사이에 놓여, 규칙이
컨텍스트 중앙에 묻히는 구조였다. 이에 예시 뒤·질문 앞에 규칙을 압축한 reminder를
재삽입했다.

## 5. 절제 실험 (Ablation)

설계한 규칙들이 실제로 기여하는지 확인하기 위해 3-shot 설정에서 개입을 단계적으로
추가·변경하며 측정했다.

| 버전 | 변경 내용 | 3-shot 정답률 |
|---|---|---|
| v0 | Plan-and-Solve 지시 + 열린 자기검증 | 66.0% |
| **v1** | 종결 규칙 + 극값 프로토콜 + 형식 계약 (자기검증 제거) | *(측정 중)* |
| v2 | v1 + 제약 나열 정교화 + 해의 원식 대입 확인 | 64.0% |
| v3 | v1 + few-shot 예시 풀이를 목표 구조로 전면 재작성 | 56.0% |
| v4 | v1 + 문제 유형별 분기 (search / direct) | 58.0% |

*(v1 측정 후 표 갱신 예정)*

### 관찰

**개입을 더한다고 성능이 단조 증가하지 않았다.** v2 이후 모든 변경이 성능을 낮췄으며,
각 실패의 메커니즘은 다음과 같이 특정되었다.

- **v2 (자기검증 추가)**: 해를 원식에 대입해 확인하도록 지시하자 Q19의 부호가 통째로
  붕괴하고 Q21이 16 → 256으로 틀렸다. 파싱 실패 문항이 2건 → 6건으로 증가했는데,
  검증 단계가 출력 길이를 늘려 절단을 유발했다. **8B 규모에서 열린 자기검증은
  교정이 아니라 이탈로 작동한다.** 이는 원 과제의 Reflector가 ISREL/ISSUP 두 개의
  boolean과 엄격한 conjunctive 수렴 규칙이라는 **좁은 판정 집합**으로 설계되었기에
  작동했다는 점과 대비된다.

- **v3 (예시 재작성)**: 지시문이 요구하는 구조와 예시(MATH 원본 풀이)의 형식이
  충돌한다고 보아, train 문항 5개의 풀이를 목표 구조로 다시 작성했다. 극값 카테고리는
  실제로 개선되었으나(Q4·Q46·Q47 정답), Q22 `99²+99+1`, Q49, Q30, Q16, Q2 등
  **단순 계산 문항이 무더기로 회귀**했다. 원본 풀이는 문항 난이도에 따라 길이가 자연히
  조절되는데, 통일된 구조의 예시가 그 신호를 제거해 한 줄이면 끝날 계산까지 단계로
  분해하다 산술을 틀린 것이다.

- **v4 (유형 분기)**: 극값 문항만 구조화 트랙으로 보내고 나머지는 원본 CoT 스타일을
  유지하도록 분기했으나, 유형 분류 자체가 새로운 오류원이 되어 개선되지 않았다.

- **길이 제약 (v1 초기안)**: 풀이를 150단어 이내로 제한하자 절단은 사라졌으나
  Q39(1260 → 630), Q44, Q3가 세 설정 모두에서 체계적으로 회귀했다. 다단계 산술이
  필요한 문항에서 압축 지시가 단계를 건너뛰게 만들었다. 종결 규칙만으로 절단이
  이미 방지되므로 길이 제약은 제거했다.

### 시사점

원 과제에서 few-shot 예시 제거가 −29 EM으로 가장 큰 손실이었던 이유는, 예시가 지식이
아니라 **출력 형식을 안정화**하고 그 형식을 하위의 결정론적 모듈이 소비하기 때문이었다.
본 실험은 그 관계의 이면을 보여준다. 여기서도 성능을 지배한 것은 지시문이 아니라
예시의 형식이었으나(v3에서 예시만 바꿔 12%p 하락), 그 방향은 개선이 아니라 손실이었다.
**형식 통일이 항상 이득인 것은 아니며, 예시가 담고 있던 난이도-길이 대응 신호를
제거하면 오히려 손해가 된다.**

## 6. 결론

- CoT는 Direct 대비 모든 설정에서 큰 우위를 보였다. 중간 계산을 토큰으로 외재화할 수
  있다는 점, 그리고 few-shot 예시가 형식이 아니라 절차를 시연한다는 점이 원인이다.
- My Prompting에서 실제로 기여한 개입은 **종결 규칙**과 **파서 계약**이었다. 특히
  종결 규칙은 정답을 산출한 뒤 대안 탐색으로 이탈해 무한 반복에 빠지는 실패
  (Q37, Q14)를 직접 회수했다.
- 반면 자기검증·길이 제약·예시 구조 통일·유형 분기는 네 차례 모두 성능을 낮췄다.
  8B 규모에서 프롬프트 개입은 단조 증가하지 않으며, 개입의 개수가 아니라 **개입이
  얼마나 좁게 트리거되는가**가 성능을 결정한다.

### 한계

- 표본이 50문항이라 3–4문항 이내의 차이는 노이즈와 구분되지 않는다.
- 평가 대상이 Level 1–3으로 제한되어 CoT의 정답률이 이미 높은 구간이며,
  프롬프트 개입의 여지가 그만큼 좁았다.
- Direct 측정값에는 API 실패가 포함되어 있어 과소평가되었다.
